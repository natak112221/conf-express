# Практика 15. Оптимизация кода и производительности

## 1. Неиспользуемые переменные и повторы

Подключил ESLint (`npm run lint`, правило `no-unused-vars`). Он нашёл одну ошибку: в обработчике ошибок в `src/app.js` параметр `next` не используется (`01-eslint-до.png`). Express требует четыре параметра, поэтому переименовал в `_next` и разрешил такие имена в `eslint.config.js`. Теперь `npm run lint` чистый (`02-eslint-после.png`).

Руками нашёл ещё:

- метод `withEvent` в модели заявок делал то же, что `find`, - удалил;
- метод `clearExpired` в хранилище сессий нигде не вызывался, просроченные сессии копились. Подключил: `server.js` чистит их раз в час;
- одинаковый блок «заявки пользователя с признаком can_review» стоял в двух методах контроллера, вынес в `itemsFor`;
- в `db/seed.js` были лишние обёртки над `prepare`, убрал.

## 2. Минификация CSS и JS и сжатие

Скрипт `npm run build` (esbuild) собирает `style.min.css` и `app.min.js`, шаблон подключает их. Исходники остались рядом, чтобы читать и править. Дополнительно подключил `compression` (gzip ответов) и заголовок `Cache-Control` на неделю для картинок и шрифтов.

| Файл | Было, байт | Стало, байт | Передаётся по сети (DevTools) |

| app.js, app.min.js | 795 | 565 | 1,7 кБ до, 1,5 кБ после |
| HTML главной | | | 8,0 кБ до, 2,8 кБ после |

Главная страница целиком в DevTools (кеш отключён, 16 запросов): было 646 кБ, стало 631 кБ (`06-devtools-до.png`, `07-devtools-после.png`). Основной вес это картинки и шрифты (около 600 кБ), текстовые файлы маленькие, поэтому выигрыш в сумме небольшой. Время загрузки на локальном сервере не уменьшилось: DOMContentLoaded в DevTools 61 мс до и 76 мс после, повторные замеры дают 80-110 мс, то есть в пределах разброса. Выигрыш виден только в переданных байтах.

После минификации открыл страницы и сравнил с версией до: вид не изменился.

## 3. Запросы к базе

Сначала попробовал индексы по `applications(event_id)` и `applications(status_id)`. Скрипт `tools/bench-queries.js` создаёт базу на 3000 пользователей и 18 000 заявок и 200 раз выполняет запросы панели. План запроса с индексом изменился (`SCAN a` стал `SEARCH a USING INDEX ...`), но время не упало: с индексами 7-29 мс, без индексов 6-16 мс, разброс от запуска к запуску больше разницы. Выборка отдаёт сразу треть или восьмую часть таблицы, и последовательный просмотр не хуже. Индексы не оставил.

Настоящая причина медленной панели в другом: она выбирала все заявки сразу (около 45 мс на 18 000 строк и тысячи карточек на странице). Сделал постраничный вывод: 20 заявок на страницу (`LIMIT` и `OFFSET`), общее число считается отдельным запросом `COUNT(*)`, внизу кнопки «Назад» и «Дальше», фильтры сохраняются.

| Запрос | Мс на запрос |
|---|---|
| все заявки сразу | 45,6 |
| одна страница из 20 | 0,28 |
| подсчёт заявок | 1,3 |
| страница с фильтром по статусу | 0,19 |
| страница с фильтром по мероприятию | 0,16 |

Снимок: `04-замер-запросов.png`. Замеры на моём компьютере, цифры немного меняются от запуска к запуску.
